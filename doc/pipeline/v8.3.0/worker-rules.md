# Общие правила AI Pipeline v8.3.0

## Цикл

Technical Architect до окончательного ТЗ → один handoff пользователем в ChatGPT → финальный контракт и явное разрешение → implementation и ограниченные наблюдения → checkpoint commit/push и Draft PR → ручная проверка → acceptance → отдельный test-only follow-up → Final Review → human merge.

Technical Architect не повторяется после каждого coding-repair. Для high complexity обязателен опубликованный handoff с хешами исследованных входов и решениями каждого finding. Для простого известного изменения допустим явно обоснованный skip.

## Ответственность

ChatGPT определяет бизнес-требования и финальный scope. Runner владеет Git/очередью и запуском команд. Исполнитель делает только разрешённые изменения; Kimi не получает Bash. Codex использует workspace-write/read-only по роли, без bypass sandbox. Это не абсолютная изоляция всего HOME: не запускать недоверенные плагины/hooks.

В implementation тесты/fixtures/test setup заморожены. Не создавать скрытый комплекс тестов под названием runtime harness. Существующие тесты можно читать/запускать без изменения, если эти команды явно объявлены. Устаревшие expectations документируются до запуска. Неизвестные падения не скрываются.

## Исправления

Только наблюдённый code_defect допускает один автоматический repair в той же session. После provider/auth/network, отсутствия среды, превышения шагов/ресурсов — остановка и сохранение работы. Нет автоматического fresh-start. Session берётся только из вывода собственного CLI; отсутствие ID остаётся null, не ищется «последняя» чужая сессия.

При невозможности завершить публикацию не повторять реализацию. Остановить и восстановить этот же run явно. Нельзя расширять scope, ослаблять assertions или менять зависимости ради зелёного статуса.

## Git и очередь

Staging только git add -A с guards до и после. Не reset --hard, не git clean, не force-push, не автоматическое удаление пользовательских изменений. Основная работа идёт в чистой рабочей копии проекта, очередь изменяется в отдельном worktree.

Один executor на репозиторий во всей системе. Claim хранится на ai-task-queue; все конкурирующие задачи этого repo ждут. Устаревший claim не перехватывается по таймауту. Подтверждение остановки старого владельца и ручной recovery обязательны. Git-claim не является fencing внешнего брокера и не делает ордер идемпотентным.

## Хранение и защита

Все захваты вывода ограничены байтами, отчёты не читают сами себя, пишутся атомарно. Лимит одного stdout+stderr — 64 MiB, handoff — 2 MiB, run — 1 GiB, runs — 20 GiB, резерв — max(10 GiB, 5% диска). Время одной фазы — 1 час, автоматического task-run — 4 часа. Проверка общего размера/RSS выполняется периодически, поэтому возможен overshoot; это не квота файловой системы.

GC через 3 дня после явного closure удаляет raw закрытых успешных и закрытых неуспешных runs, оставляя небольшой history receipt. Pending acceptance, незавершённая работа, активные runs, backups и vendor sessions защищены. При исчерпании безопасного места остановиться, не удалять защищённую работу.
